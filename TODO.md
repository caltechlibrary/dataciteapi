- [ ] **Report HTTP failures as errors a caller can classify** (found 2026-10-27 in irdmtools, doi2rdm Part B, which has to tell "no such DOI" from "service unavailable" to give the workspace exit codes, DR-0014). Today `getJSON` records the status on the client (`Status`, `StatusCode`) but returns `src, nil` with `src` empty for **any** non-200 response (404, 429, 5xx alike), so `Dois`, `Works` and the other methods return `nil, nil`, and the caller sees neither an error nor a record. A caller has to read `client.StatusCode` after the call, which is easy to miss (`irdmtools` does exactly that for now). `crossrefapi` v1.1.0 has the same shape.
  - Return an error for a non-200 response, wrapping a sentinel with `%w` so `errors.Is` works: `ErrNotFound` (404), `ErrRateLimited` (429, ideally carrying the `Retry-After` value), `ErrUnavailable` (5xx), and a plain `*HTTPError` (status and body excerpt) for the rest.   - Leave a network error from `client.Do` as the `net.Error`/`*url.Error` it already is, so a caller can classify it (DR-0014: those are 69).
  - Decide whether a 200 with an empty `data` is a not-found; `QueryDataCiteObject` in irdmtools treats "no objects" as an error today.
  - This changes what existing callers see (a 404 used to be `nil, nil`), so it is a minor release with an upgrade note, and a test for each status with `httptest`.
